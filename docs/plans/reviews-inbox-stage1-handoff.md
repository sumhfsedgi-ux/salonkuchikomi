## 3. 第1段階:完了したこと

利用者の判断で、2026-10-16 の報告をもって第1段階の画面・機能の調整は完了。

- Google 連携(共通の連携の上)→ 同意 → 店舗の選択 → 取り込み(続きの取得)→ 一覧・詳細 → 返信案 → 編集 → 確認ダイアログ → 投稿・変更・削除。
- 返信欄は1つ。
  - 「返信案を作成」「作り直す」で同じ返信欄に入れる。
  - 手で直した文章を置き換える前に確認する。
  - 「前の文章に戻す」は直前の1つだけ。
  - 作成中は読み取り専用にする。結果を入れる直前に、口コミ・連携先・返信欄を確かめる。
  - 下書きは自動保存し、1つずつ順に保存する。
- 結果不明は、取り直して送った内容が見えたときだけ確認済みにする(時間では終えない)。それまで、再送・変更・削除・取り下げを画面とサーバーの両方で受け付けない。
- 連携の解除・店舗の変更・アカウントの切り替えと、実行中の同期・生成・投稿の重なり(選択の世代で拒否)。
- 403 の分類(権限不足は口コミの結び付けだけに記録し、Gmail は変えない)。
- 期限切れの内容の削除のジョブ `/api/jobs/gbp-maintenance`。利用可否に関係なく動き、`GBP_MAINTENANCE_SECRET` で認証する。
- 利用可否は DB の機能一覧で判定する(google_reviews は `coming_soon`、プランの標準は使えない、店舗ごとの許可)。

## 5. マージと本番反映の順序

前提:master へのマージで、すぐに本番へ自動デプロイされる。新しいアプリが前提にする DB は、マージの前に本番へ入れておく。DB を先に入れても、旧アプリが壊れないことを各段で確かめる。

### 段 A:PR #9(0025・0026)
`docs/plans/salon-onboarding-runbook.md` の B の順に行う。
1. 独自の SMTP・Redirect URLs(`/auth/confirm`)を設定する。
2. 本番で `0025-precheck.sql` を流す。
3. 本番の環境変数に `AUTH_EMAIL_VERIFY=1`・`AUTH_EMAIL_VERIFY_RECIPIENTS` を入れる。`SELF_SIGNUP_ENABLED` は入れない。
4. SQL Editor で 0025 → 0026 をファイル全体で1回ずつ適用し、verify を流す。
5. すぐに PR #9 を master にマージする(自動デプロイ)。
   - **merge commit でマージする(squash しない)**。このブランチは PR #9 のコミットをそのまま含むため、squash すると載せ直しで衝突が増える。
6. テンプレートの変更・確認・検証の設定を外す(runbook の段5〜8)。

段 3〜4 の間は、旧アプリで新しい店舗を登録できない(runbook の「3〜4 のあいだの、旧アプリへの影響」)。この間は運営が登録しない。

### 段 B:このブランチ(0027〜0031)。段 A の完了と、本番の安定を確かめてから
1. PR の base を master に変え、master をこのブランチにマージする(rebase・force-push はしない)。migration の番号の重なりを確かめ、tsc・vitest・test:localdb・build を流す。
2. 本番の事前の確認(読み取りのみ)を行う。
   - 0024〜0026 が適用済みであること。
   - `review_reply_settings`・`gbp_*` の表、`feature_catalog` の `google_reviews` の行が無いこと。
   - Supabase CLI の記録(`supabase_migrations`)が無いこと。
3. 本番の環境変数(Vercel の Production)を設定する。次のデプロイから効く。
   - `REVIEW_KEY_HMAC_SECRET`:32文字以上の新しい値。口コミを取り込むときにだけ使う。無くても今のデプロイは壊れない。
   - `GBP_MAINTENANCE_SECRET`:新しい値。期限切れの削除のジョブの認証。無いと、そのジョブはエラーを返すだけ。
   - `GOOGLE_REVIEWS_OAUTH_ENABLED` は**入れない**(公開まで空)。
4. 本番の SQL Editor で 0027 → 0028 → 0029 → 0030 → 0031 を、ファイル全体で1回ずつ、続けて適用する。
   - 0028 と 0031 の間に、アカウントの削除・Google 連携の解除を行わない。
   - 適用のあとに確かめること:
     - google_reviews が `coming_soon` で、プランの標準が false、店舗ごとの許可が0件。
     - `gbp_*` の表が空。
     - `gbp_binding_changed` が security definer。
   - この時点の旧アプリ(段 A のアプリ)は、新しい表・関数を使わない。google_reviews の行は `coming_soon` なので、どの店舗でも使えない。
5. この PR を master にマージする(自動デプロイ)。google_reviews は `coming_soon` で、`GOOGLE_REVIEWS_OAUTH_ENABLED` も空。そのため、どの店舗にも新しい入口・画面は出ない。
6. デプロイのあとに確かめる。
   - 既存の店舗のホーム・メニュー・口コミ(アンケート)が今までどおりであること。
   - 予約通知が続いていること。
   - 運営管理の利用権限に「Google口コミ」が準備中で出ること。
   - Google 連携の画面に口コミのカードが出ないこと。
7. 期限切れの削除のジョブを、外部のスケジューラーで毎日呼ぶ(Bearer `GBP_MAINTENANCE_SECRET`。対象が無ければ何も消さない)。

## 6. 第2段階の方針(2026-10-16 の利用者の指示。計画 第2版 §3「第2段階」より優先)

- 内容:新着の口コミの自動取得と、LINE 通知。
- LINE に載せるもの:店舗名、「新しい口コミが届きました」、口コミの画面へのリンク。**これだけ**。
- LINE に載せないもの:口コミの本文・評価(★)・投稿者名・件数。計画 第2版の「★と抜粋(G2)」は使わない。
- 計画の更新はクラウド側で行う。実装はまだ始めない。

計画を更新するときの材料(第1段階のコードにあるもの):
- 新着の判定:`gbp_review_index.first_seen_at`・`seen_at`、`gbp_locations.initial_sync_done_at`。
- 重複を防ぐキー:`lib/gbp/reviewKey.ts`(HMAC)。
- 同期:再開できる同期・処理権。手動の［更新］は5分に1回まで。
- 期限切れの削除のジョブ。
- LINE の通知先:master の 0023(招待・解除・登録の世代)。予約通知の配信の表(0020 の `notification_deliveries`)とは混ぜない(計画 §3)。

計画で決める必要があること:
- 自動取得の方式(Google の Notifications API・Pub/Sub か、定期の取得か)。
- 送信の重複防止と、停止の条件。
- 新着の判定と、識別子・日時の保持期間(§7 の Google の規定との関係を含む)。
- リンク先のログインの扱い。
