# 新規登録・運営によるサロン登録と招待・利用区分(0025・0026)の本番反映(手順)

作成: 2026-10-14。更新: 2026-10-15(0026: 運営の承認をなくした登録の流れ)。設計は `docs/plans/salon-onboarding-plan.md`、メールの文面は `docs/plans/salon-onboarding-email-templates.md`。
**この手順は運営が実施する。** 開発の作業(ブランチ `feature/salon-onboarding`)では、本番の DB・Auth の設定・メール・デプロイには触れていない。

**全体を通して守ること**
- 0001〜0024 は書き換えない。0025・0026 は新しい migration として適用する。
- 通常の手順は、**まだ適用していない migration を番号の順に適用する**(0025 → 0026)。適用済みの migration は再実行しない。
  誤って古い migration を再実行してしまった場合は、影響を確かめてから「I. 復旧の手順」に従う(通常の手順ではない)。
- 決済が整うまで、一般向けの新規登録は公開しない(`SELF_SIGNUP_ENABLED` を入れない。DB の `self_signup_settings.open` は閉じたまま)。公開の前に「J. 一般公開の前に確かめること」を済ませる。
- 影響は断定しない。各段で確かめてから次へ進む。
- 秘密の値・パスワードはチャットやリポジトリに書かない。運営はお客様のパスワードを作らない・見ない。

### 0025・0026 の実行のしかた(段3)
- まだ適用していない migration を、番号の順に1つずつ実行する(0025 → 0026)。
- SQL Editor に **ファイル全体** を貼り付けて1回で実行する。範囲を選んで一部だけ実行しない。
- SQL Editor は複数の文を1回の単純クエリとして送る。そのため全体が1つの暗黙のトランザクションになり、途中で失敗すると何も残らない。この動きは、localdb と testdb で同じ実行方式を使って確かめた(最後に失敗する文を足すと、列・表・ポリシー・履歴のどれも残らない)。
- 実行が失敗したときは何も残らない。原因を確かめてから、同じファイル全体を実行する(最初の処理は、列がまだ無いときだけ行う。0025: 列の追加・既存店舗の無料提供・legacy の記録 / 0026: `plan_placeholder` の追加と埋め戻し)。
- ファイルの中には `begin`/`commit` を書いていない。

### 3〜4 のあいだの、旧アプリへの影響
- 新しい店舗を登録できない。ブラウザから店舗を作るポリシーを削除し、制限のトリガーも作成を拒否するため。この間は登録しない。
- サインアウトしたセッションの古いアクセストークンが、すぐに使えなくなる(セッションの行の有無を見るため)。
- 既存のオーナーと運営の管理者は `legacy` として記録される。そのため、セッションが残っている限り使える範囲は変わらない。

### C. デプロイ後の確認(段7。運営のアドレスだけを使う)
- 既存の店舗: 運営の検証用の店舗でログインし、ホーム・口コミ・お客様用ページ・生成が今までどおり使えること。予約通知の稼働中の店舗の通知が続いていること(cron の結果、`notification_deliveries`)。
- /ops の一覧で、既存の店舗がすべて「無料提供」・登録経路「既存の店舗(移行)」と出ること。変更履歴に「利用区分を無料提供に設定(変更者: 移行(0025))」が出ること(メモは 0025 が記録した文のまま「…無償提供として移行」と出る。記録は書き換えない)。
- 「サロンを追加」で、運営のアドレス(`AUTH_EMAIL_VERIFY_RECIPIENTS`)を招待先にして、次の流れが通ること。
  1. 下書き
  2. 内容を確認
  3. 登録して招待メールを送信
  4. 届いた招待のリンク → パスワードの設定 → 利用開始待ちの画面
  5. 運営の検証用の店舗として、/ops で利用区分を「テスト用に変更」する → ダッシュボードが使える(通常のお客様の利用開始の代わりには使わない)
- 「サロンを追加」の登録種別に「無料提供」が無いこと。既存の店舗の詳細では、止めたあと「無料提供に戻す」が選べること。
- 新規登録の受付が閉じていること: 店舗を持たないアカウントでログインすると、店舗の情報の画面に受付停止の案内が出ること。
- 新規登録そのものの確認は、決済の実装のあと(J)に行う。
- 確認が済んだら段8。

## D. 運用で変わること
- 新しいお客様のアカウントは、Supabase の管理画面で作らない。/ops の「サロンを追加」から招待する。
  - 管理画面で作ったアカウントは、本人がメールのリンクで本人確認(パスワードの設定)を済ませるまで、店舗を操作できない。
  - ログインすると、本人確認の画面に「本人確認のメールを送る」が出る。
- 運営のアカウントは、次の順に作る。
  1. 管理画面で招待する。
  2. 本人が受け取る前に、`scripts/operator-admin.ts grant` で管理者として登録する。
  3. 本人が受け取ると `/auth/verify`(パスワードの設定)→ `/ops` に進む。
  - 管理者は店舗の所有者になれない(DB でも拒否する)。
- 通常のお客様の利用開始に、運営の操作は無い。将来、プランの選択・決済の完了で自動で利用を始める(決済は未実装。それまで通常の店舗は利用開始待ちのまま)。
- 運営が /ops の詳細の「利用区分」で行えるのは、次の3つだけ。
  - テスト用の指定(運営の動作確認用。プランが決まっている店舗だけ。お客様の利用開始の代わりには使わない)
  - 利用の停止(利用開始待ちに変更)
  - 既存の店舗(0025 の時点の店舗)を無料提供に戻すこと(新しい店舗は無料提供にできない)
  - どれも区分だけを変える。契約プラン・機能の利用許可・権限による停止・予約通知の稼働状態は変わらない。予約通知は自動では開始・再開しない。
- 新しい店舗が利用開始待ちのあいだは、「契約と利用許可」は読み取り専用(プランは予定で、契約ではない)。
- 既存の店舗を止めている間は、プランと機能の利用許可を調整できる。保存しても利用は再開せず、予約通知の権限による停止も解除しない(再開は「利用区分」で無料提供・テスト用に戻すことと、停止の解除で行う)。
- 利用開始のお知らせのメールは、今は無い。将来、決済の完了で自動で利用が始まったときに送る(運営の承認の通知にはしない)。
- 本人確認のリンク(運営の再送・本人確認の画面のボタン)は、パスワード再設定と同じ形式のメールで届く。お客様に伝えるときは、そのことも伝える。

## E. 既存店舗の移行(0025 の中で行う)
- 対象: 0025 を最初に適用した時点で存在する全店舗(A-2 の一覧)。
- 内容: 利用区分を「無料提供」、登録経路を「既存」にする。店舗ごとに操作履歴を1行書く(`migration:0025`)。
- 変えないもの: 契約プラン、機能の個別設定、権限による停止、Google・LINE の連携、予約通知の稼働状態。利用区分が利用中なので、利用可否も変わらない(A-3・A-4 と比べる)。
- 再実行しても、あとから作られた店舗・アカウントは変えない(列が無いときだけ行う)。
- 0026 も既存の店舗を変えない(`plan_placeholder` は false。通常利用への一括の変更・課金の対象への変更はしない)。
- 運営の検証用の店舗も「無料提供」になる。テスト用として扱う場合は、適用のあと /ops で区分を「テスト用に変更」する(機能・権限は広がらない。操作によっては実際のメール・LINE の送信が発生する)。

## F. 切り戻しの条件
`owner_insert`・`owner_delete` のポリシーを戻すだけでは、安全とは判断しない。ポリシーを戻しても、0025 の制限で旧アプリは店舗を作れない。

**新しい方式のデータがまだ無いとき**(`docs/plans/sql/0025-rollback-support.sql` の 1 がすべて 0)
- アプリを戻し、テンプレートを控えた文面に戻す。
- 0025 の DB はそのまま残す。既存のオーナーは `legacy` なので、旧アプリでも同じ判定になる。
- 旧アプリに戻した期間は、新しい店舗の登録を止める。

**新しい方式のデータがあるとき**: 無条件には戻さない。旧アプリでは次のことが起きる。
- 招待のリンクが壊れる(`/auth/confirm` が無い)。
- 本人確認の済んでいないアカウントは、店舗の画面が空になる(理由が表示されない)。
- 利用開始待ちの店舗は、案内の画面が無く、使える機能が無い表示になる。
- 下書きと招待の状況が見えなくなる。

戻す必要があるときは、次の順に進める。原則は修正版を出す。
1. `0025-rollback-support.sql` の 2・3 で、該当するアカウントと店舗を一覧にする。
2. 招待と新規登録を止める(`SELF_SIGNUP_ENABLED` を外し、運営の登録を止める)。
3. 店舗ごとに対応を決める(区分を変える、お客様に連絡する)。

**0025 そのものを戻す SQL は用意しない**: 0024 の判定に戻すと、利用開始待ちの店舗が使えるようになるため。必要になったときは、別に作って試験する。

**0026 について**: 新しい表・列・関数の追加と、0025 の関数の作り直し。アプリを戻すときも、0026 の DB はそのまま残す(戻す SQL は用意しない)。

## H. マージのときの migration の番号(2026-10-14 に確認。0026 は 2026-10-15 に確認)
- 0025・0026 を使っているのは、この作業だけ(ローカル・リモートのどのブランチにも無い。master は 0024 まで)。
- 0026 は登録フロー側が使う。口コミの AI 返信の作業は、予約済みの 0013〜0017 を使い、新しく足す migration は 0027 以降にする。ほかのブランチの migration は、この作業では変えない。
  - 最新の master(78df7e5)の migration は 0024 まで。0013〜0017 は、口コミの返信の作業(`feature/reviews-d1-reply-engine`)のために空けてある。
  - ほかのブランチ・worktree にも、0025 以降の migration は無い。
  - 口コミの返信の作業の 0013〜0017 は、0025 が作り直す表・関数・ポリシーに触れない(どれも新しい表と service_role だけの関数)。
- **番号を変えずにマージできるなら、変えない。** テスト用 DB の適用の記録(`testdb_meta.applied_migrations`)は、ファイル名と内容のハッシュで照合している。
  今の 0025 のハッシュ(改行を LF にそろえた値)は、テスト用 DB の記録と一致している。
- **ほかの作業が先に 0025 を使い、こちらの番号を変える必要が出たとき**(内容は変えない):
  1. ファイル名だけを変える(例: `0026_salon_onboarding.sql`)。中身は1文字も変えない(ハッシュが変わると、別の migration として扱われる)。
  2. テスト用 DB では、もう一度実行せずに、記録の名前だけを変える(実行しなおしても結果は同じだが、記録が2重になり、どれが適用済みかが分かりにくくなる)。
     ```sql
     -- テスト用の DB だけ。1行だけ変わることを確かめる
     update testdb_meta.applied_migrations
        set name = '0026_salon_onboarding.sql'
      where name = '0025_salon_onboarding.sql';
     ```
     そのあと `npm run testdb:migrate`(見るだけ。記録のハッシュとファイルを比べる)で、新しい名前が「適用済み」、ほかの作業の 0025 が「未適用」になっていることを確かめてから、`--apply` する。
     新しい名前が「記録のあとに変更あり」と出たら、ファイルの中身が変わっている。名前の変更を元に戻し、中身の違いを調べる。
  3. ほかの作業の 0025 が、0025(この作業)と同じ関数・ポリシー・表(例: `salon_feature_access`・salons のポリシー・`admin_list_salons`)を作り直す場合は、
     本番では「ほかの作業 → この作業」の順になる。テスト用 DB でも同じ順にするため、ほかの作業の migration を適用したあとに、
     この作業の migration をもう一度実行する(何度実行しても同じ結果になるように書いてある)。そのうえで testdb・localdb のテストをやり直す。
  4. 本番: これまでどおり SQL Editor でファイルごとに適用するなら、番号は DB に残らない。`0025-precheck.sql` の 10 で、
     Supabase CLI の記録(`supabase_migrations.schema_migrations`)が無いことを確かめる。あれば、その記録と食い違わない番号にする。
- 手順書・SQL・README の中の「0025」も、あわせて新しい番号に直す(`docs/plans/sql/0025-*.sql` のファイル名を含む)。

## I. 復旧の手順: 古い migration を誤って再実行した場合(通常の手順ではない)
1. 新しい店舗の登録・運営の操作を止める(この間に区分や登録を変えない)。
2. 影響を確かめる(読み取りのみ): `0025-verify.sql`・`0026-verify.sql` を流し、適用の前に控えた結果と比べる。
   - 0011・0023・0024 を再実行した場合: 0025 が作り直した関数・ポリシー(`salon_feature_access`・salons の書き込みの制限・オーナーのポリシーなど)が古い形に戻り、利用開始待ちの店舗が使えるようになることがある。
   - 0025 を再実行した場合: 0026 が作り直した関数(`create_own_salon`・`admin_register_salon`・`admin_update_salon_service_status`・`admin_list_salons`・`salon_draft_invalid_field`)が 0025 の形に戻る(受付の閉鎖・新しい店舗の無料提供の禁止・プランの仮の値の扱いが効かなくなる)。データは変わらない。
3. 影響を確かめたうえで、再実行したものより後の migration を番号の順に適用し直す(例: 0024 を再実行したら 0025 → 0026、0025 を再実行したら 0026)。どれも何度実行しても同じ結果になるように書いてある。
4. もう一度 verify の SQL を流し、事前の結果と同じことを確かめてから、操作を再開する。

## J. 一般公開の前に確かめること(決済の実装のあと)
- 決済(プランの選択・支払い・自動の利用開始)と、利用開始のお知らせのメールができていること。
- Supabase の設定(管理画面で確認し、控える):
  - 同じ人への最低の間隔(Email の「Minimum interval」など。資料・ソースでの初期値は60秒)が、`AUTH_EMAIL_MIN_INTERVAL_SECONDS`(初期値65秒)より短いこと。長い場合は、アプリの間隔を長くする(Supabase に断られても、画面は登録済みかどうかを漏らさないため受付と同じ表示になり、メールは届かない)。
  - プロジェクト全体の、1時間あたりのメールの上限(Rate limits)。サーバーから呼ぶため、Supabase の IP ごとの上限はサーバーの IP にかかる。
  - 「Allow new users to sign up」の値と、OFF のときに運営の招待(`inviteUserByEmail`)が動くか(未確認。専用のプロジェクトで確かめる)。
  - 独自の SMTP・差出人名・送信元アドレス(`docs/plans/salon-onboarding-email-templates.md` の「差出人と問い合わせ先」)。
- そのあと、`SELF_SIGNUP_ENABLED=1` を入れて再デプロイし、SQL で `update public.self_signup_settings set open = true, updated_at = now() where id = 1` を実行する。止めるときは逆の順にする。
