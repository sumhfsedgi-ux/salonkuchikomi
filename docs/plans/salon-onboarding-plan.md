# お客様の新規登録・運営によるサロン登録と招待・利用区分 — 設計

作成: 2026-10-14。更新: 2026-10-15(0026: 運営の承認をなくした登録の流れ)。ブランチ: `feature/salon-onboarding`(master 78df7e5 から)。
本番の手順は `docs/plans/salon-onboarding-runbook.md`、メールの文面は `docs/plans/salon-onboarding-email-templates.md`。

## 0026: 登録から利用開始までの流れ(2026-10-15 に確定した方針)
- **通常のお客様の利用開始に、運営の承認は無い。** 将来、プランの選択・決済の完了で自動で利用を始める。
  - お客様が自分で登録: アカウント作成 → メールの確認・本人確認 → 店舗の情報 → (将来)プランの選択・決済 → 自動で利用開始
  - 運営が店舗を登録: 運営が作成・招待 → お客様が本人確認・登録の手続き → (将来)プランの確認・決済 → 自動で利用開始
  - 既存の店舗(0025 の時点の店舗): これまでどおり無料提供で使える(通常利用への一括の変更・課金の対象への変更はしない)。
  - テスト店舗: 運営が指定し、決済なしで許可した機能を使える。お客様は自分でテスト店舗にできない。外部への送信を止める仕組みではない。
  - 今後登録する一般のお客様への無料提供はしない。
- **決済の実装まで(今回)**
  - 一般向けの新規登録の受付は公開しない(`SELF_SIGNUP_ENABLED` も、DB の `self_signup_settings.open` も閉じたまま)。
  - 登録しただけでは、どの新しい店舗も使えない(利用開始待ちのまま)。運営が登録した通常の店舗も同じ。
  - 運営の承認・「通常利用に変更」のような操作は、決済の代わりとして作らない。仮の決済・支払い済みの印・動かない購入のボタンも作らない。
  - 承認や、送る仕組みの無い通知(利用開始のご案内など)を約束しない。利用開始待ちの画面は「店舗情報の登録が完了しました」「現在、プラン選択・お支払いの手続きを準備しています」と伝える。

### 利用区分(誰が、どの区分に変えられるか)
| 区分 | 意味 | 変えられる人・条件 |
|---|---|---|
| 利用開始待ち(pending) | 新しい店舗の既定。使えない | 運営(利用中の店舗を止める) |
| 無料提供(complimentary) | 0025 の時点の店舗だけ | 運営(止めた既存の店舗を戻すときだけ。新しい店舗は DB で弾く) |
| テスト用(test) | 運営の動作確認用。決済なしで許可した機能を使える | 運営(プランが決まっている店舗だけ。お客様の利用開始の代わりには使わない) |
| 通常利用(未実装) | 将来、決済の完了で利用中になる状態 | 将来の決済の処理だけ(運営の画面からは選べない) |
- 新しい店舗の登録種別は「通常登録(pending)」と「テスト用」だけ。保存済みの下書きの「無料提供」は、未選択として開き、選び直してもらう。
- 選べる変更は `serviceStatusChoices`(`lib/onboarding/serviceStatus.ts`)と `admin_update_salon_service_status`(DB)で同じ規則。
- 利用開始待ちから利用中にしたときは、そのときの契約プランを履歴に残す(`target = contract_plan`)。

### プランの「予定」と「契約」(列の意味)
- `salons.plan`: 利用中の店舗では契約プラン。利用開始待ちの店舗では、利用を始めるときに使う予定のプランで、契約ではない。
- `salons.plan_placeholder`(0026): true のとき `plan` は判定の内部だけで使う仮の値で、プランは未定。契約が確定したか・支払い済みか・利用開始かは、この列では表さない(利用区分で決まる)。既存の行はすべて false。
- 制約 `not plan_placeholder or service_status = 'pending'`: 仮の値のまま利用中にならない。
- お客様の登録は、プランを決めない(`plan_placeholder = true`)。運営の通常登録のプランは「案内予定のプラン」(任意)、テスト用は「契約プラン」(必須)。プランが未定のときは、機能ごとの利用許可を登録しない。
- 表示は `planDisplay`(`lib/ops/onboardingDisplay.ts`)だけで決める: 契約プラン / 契約プラン(利用停止中)/ 案内予定のプラン(契約ではありません)/ 未定。お客様の画面にはプランを出さない。
- 新しい店舗(登録の途中。`registration_source` が existing 以外)が利用開始待ちのあいだは、「契約と利用許可」を読み取り専用にする(画面・保存の Action・`scripts/salon-contract.ts`)。予定のプランを「現在の契約」と出さず、0024 の「契約プラン: A → B」の履歴も残さない。登録のあとに予定のプランを変える操作は、今回は無い。
- 既存の店舗(0025 の時点の店舗。`registration_source = existing`)は、止めている間(利用開始待ち)もプランは契約のまま。運営はプランと機能の利用許可を調整できる。
  - 保存しても、利用区分は利用開始待ちのまま、権限による停止(予約通知など)も開いたまま。再開は、区分の変更(無料提供・テスト用に戻す)と、停止の解除という別の明示的な操作だけ(localdb と、共有のテスト用DBの通しの確認で確かめた)。運営の画面の「連携と稼働状況」と停止の解除の欄も、止めている間は「利用区分」の変更を案内する(「契約プラン・使える機能」の保存では再開しない)。
  - 区別は `registration_source` で行う(0025 で、その時点の全店舗が existing になり、以後の店舗は self_signup / operator。お客様からは変えられない)。止めたテスト店舗など、新しい店舗が止まっている間は、テスト用に戻してから調整する。
- 一覧のプランでの絞り込みは、契約プランだけを対象にする(利用中の店舗と、止めている既存の店舗)。

### 新規登録の受付を閉じたときに止める経路・止めない経路
| 経路 | 主な対象 | 閉じているとき |
|---|---|---|
| 新規登録(`/signup`・`signupAction`) | 新しいアドレス | 受け付けない(`SELF_SIGNUP_ENABLED`) |
| 店舗の情報の登録(`/onboarding/salon`・`registerOwnSalonAction`・`create_own_salon`) | 店舗を持たないアカウント | 受け付けない(アプリと DB の両方。`create_own_salon` は REST から直接呼べるため DB でも止める) |
| 確認メールの再送(`resendConfirmationAction`) | 自分で登録して、メールの確認がまだのアカウント | 止めない(招待のお客様は使わない経路。Supabase の再送は anon key で直接呼べるため、止めても守りにならない) |
| 招待のリンク → パスワードの設定、招待・本人確認のリンクの再送、本人確認のメール、ログイン、既存のパスワード再設定 | 招待されたお客様・すべてのアカウント | 止めない |
- 判定は `isShopRegistrationOpen`(`lib/onboarding/selfSignup.ts`。アプリの設定と DB の設定の両方が開いているときだけ。読めなければ閉じているとして扱う)。

### 送信の待ち時間(新規登録・確認メールの再送・本人確認のメール)
- 接続元ごとの回数(0012 の `rate_limit_hit`。1時間に10回・1時間区切り)は変えない。
- アドレス(本人確認のメールはユーザー)ごとの間隔は、0026 の `auth_email_cooldown_take`(前回から N 秒。確かめると同時に記録する)。新規登録と確認メールの再送で同じキーを使う。
  - 以前の「時計の1分区切り(1分に1回)」は、区切りの直前と直後で続けて送れ、Supabase 側の「前回の送信から数える」間隔と食い違うことがあった。
  - 間隔は `AUTH_EMAIL_MIN_INTERVAL_SECONDS`(初期値65秒)。Supabase の、同じ人への最低の間隔(資料・ソースでの初期値は60秒)の実際の設定値は確かめていない。アプリの間隔のほうが長いときだけ、Supabase に断られにくくなる(手順書の公開前の確認項目)。
- 待ち時間は、サーバーが返した残りの秒数で数える(`retryAfterSeconds` と `retryScope`)。画面は、待っている間、送信のボタンを押せなくする。入力し直して同じアドレスに戻っても待ちが続き、アドレスを直したら、そのアドレスに当てはまる待ち(接続元の上限)だけを出す。残り時間を問い合わせる専用の窓口は作らない(誰かが最近そのアドレスで送ったことが分かってしまうため)。
- 応答は、アカウントの状態で変えない。上限はアカウントを調べる前に確かめ、Supabase に断られた・送れなかった場合も受付と同じ応答にする(ログには失敗の種類だけ)。そのため、受付と表示されてもメールが送られていないことがある。

## 目的と範囲
- 「ログイン」「店舗の登録」「サービスの利用」を分ける。
  - 登録が済んだ状態: salons に行がある。
  - 利用できる状態: 利用区分が利用中。
- 将来の決済は、「利用開始待ち」の画面(`/onboarding/status`)と、利用区分の判定(`salon_service_active`)に足す。
- 含むもの

  - 運営のサロンの追加(下書き → 確認 → 本登録・招待)

  - 招待と案内の状態・再送
  - 既存店舗の移行
- 含まないもの
  - 決済・料金
  - 新しいプラン
  - 複数の店舗の切り替え
  - 削除
  - 所有者の変更
  - Google・LINE の自動の連携
  - 予約通知の自動の開始
  - 届いた口コミ

## 判定の軸(どれも別に管理する)
| 軸 | 置き場所 | 変えられる人 |
|---|---|---|
| 本人確認 | `account_verifications`(アカウント単位)+ `current_session_trusted()`(セッション単位) | 本人(メールのリンクで得たセッションでの手続き)。移行の時点のアカウントは legacy |
| 店舗の登録 | `salons`(`registration_source`: existing / self_signup / operator) | お客様(`create_own_salon`)・運営(`admin_register_salon`) |
| 利用区分 | `salons.service_status`(pending / complimentary / test)。画面の言葉は場面で分ける: 新しい店舗の「登録種別」は 通常登録/テスト用、今の状態は 利用開始待ち/無料提供/テスト用、変更は「利用開始待ちに変更」など結果が伝わる言葉(`lib/onboarding/serviceStatus.ts`) | 運営(テスト用の指定・停止・既存の店舗を無料提供に戻すことだけ。`admin_update_salon_service_status`)。通常のお客様の利用開始は、将来の決済の完了で自動 |
| 契約プラン・機能の利用許可・権限による停止 | 0024 のまま。利用開始待ちの店舗のプランは予定(契約ではない。`plan_placeholder` は 0026) | 運営(利用中の店舗だけ) |
| 稼働状態(予約通知) | 0022 のまま | お客様の開始の操作・運営 |

**最終的な利用可否** `salon_feature_access` は、引数と戻り値を 0024 から変えていない。
- 0024 の判定の結果に、最後に「利用中の区分である」ことを AND する。
- 本来なら利用可の機能だけ、理由を `service_pending` にする。プランの対象外・準備中・提供終了・個別に利用不可の理由は、そのまま返す。
- 画面・API・公開ページ・生成 API・予約通知の DB 関数は、どれもこの1つの判定を使う。
- 区分の変更は、トリガーで `entitlement_touch` を通す。そのため版数・ロック・履歴・コミット時の評価(0024)が働く。利用中から利用開始待ちに戻すと、予約通知の「権限による停止」が開く。戻しても自動では再開しない。

## 本人確認とセッション(ユーザーの決定)
**規則**
- 確認済みのアカウントのパスワードは変えない。
- 未認証の人の再登録では、パスワードを変えも無効にもしない。
- 未確認のアカウントを再利用するとき、第三者が付けた可能性のあるパスワードを有効なまま残さない。
  - パスワードを無効にするのは、運営が明示的に紐付けるときだけ。
  - それ以外は、メールのリンクで本人確認した人が、新しく設定する。
- 店舗を操作できるのは、本人確認とパスワードの設定(または確認)が済んでから。

**信頼できるセッション** `current_session_trusted()` は、次のすべてを満たすときだけ true になる。
1. JWT の `session_id` の行が `auth.sessions` にあり、本人のもので、`not_after` を過ぎていない。サインアウトしたセッションの、期限内の古いアクセストークンは、ここで拒否する。
2. 本人確認の記録がある。
3. 次のどれかに当てはまる。本人確認より前の第三者のセッションは、本人確認のあとも信頼しない。
   - legacy
   - 記録を作ったセッションそのもの
   - 記録よりあとに作られたセッション

この判定を使う場所:
- 画面と Server Action: `my_account_state()` を読む。`getCurrentSalon` は、salons の RLS によって、信頼できないセッションには店舗を返さない。`requireOperator` も同じ判定を使う。
- REST・RPC: オーナー用の RLS と、ブラウザのロールが呼べる関数(`owner_*_salon_ids()`・`create_own_salon`)を通す。

**本人確認の手続き**(`lib/onboarding/verification.ts`)。記録だけを行う入口は作らない。1つのサーバーの処理の中で、次の順に行う。
1. 検証済みの JWT の `amr` が、メールのリンクの方法であることを確かめる。
2. 本人の操作を行う。
   - 入れ直す: セッションを持たないクライアントで照合する。
   - 新しく設定する: このセッションで `updateUser` する。
3. service_role の `account_verification_record` で記録する。DB でも、セッションの行・`auth.mfa_amr_claims`・メールの確認を確かめる。記録は最初の1回だけ。
4. ほかのセッションをサインアウトする。

**mode**
- `confirm_or_set`: 自分の画面で、アカウントが無い状態から新しく登録したとき。登録したパスワードを入れ直すことでも本人確認できる。
- `set_new`: それ以外のすべて。新しいパスワードの設定だけで本人確認する。
  - 運営の招待・紐付け
  - 未確認のアドレスでの再登録
  - API から直接作られたアカウント

### テスト用の Supabase で確かめた実際の動き(2026-10-13・14。`scripts/testdb/auth-verification.test.ts`)
- **amr**
  - token_hash を `verifyOtp` で検証したセッションは、確認・招待・Magic Link・パスワード再設定のどれも `otp`。パスワードでのログインは `password`。
  - JWT と `auth.mfa_amr_claims` の値は一致した。
  - 既存のパスワード再設定の画面(ブラウザの PKCE の流れ)のセッションは `recovery`(JWT・DB とも。`scripts/testdb/password-reset-walkthrough.ts`)。Supabase Auth の実装に合わせて、`invite` などもメールのリンクとして扱う。
- **乱数のパスワード**: 招待のリンクを検証すると、パスワードの無い招待ユーザーに乱数のパスワードが付く。そのため、パスワードの有無を本人確認の根拠にしない。
- **他のセッションの削除**
  - `signOut({scope:'others'})` で、ほかのセッションの行が消える。
  - パスワードを変えると、Supabase Auth がほかのセッションの行を消す。
- **古いトークン**: セッションの行が消えたあとの古いアクセストークンでは、次のどれも通らない。
  - Supabase Auth: `GET /user`・`PUT /user`(パスワード・メールアドレス)は 403 `session_not_found`。
  - リフレッシュトークン: `refresh_token_not_found`。
  - DB: `session_trusted=false`、salons は 0 行。
  - よって、計画で用意していた「認証情報の指紋」は要らなかった。
- **第三者が先に作った未確認のアカウント**
  - 本人が確認のリンクを開いたあと、第三者は P でログインできる。ただし、そのセッションでは本人確認・店舗の作成・記録の関数・店舗の読み書きのどれもできない。
  - 本人が新しく設定すると、P・古いアクセストークン・リフレッシュトークンはすべて使えなくなる。
  - 第三者が先にパスワードを変えると、本人のリンクのセッションが消える。本人の手続きは `session_expired` となり、新しいリンクで設定し直せる。このとき第三者は締め出される。
- **使用済みのリンク**: 使用済みの確認のリンクは `otp_expired`。
- **同時の設定**: 同じアカウントの2つのメールのリンクのセッションで同時に設定すると、互いのセッションを消し合い、どちらも記録されないことがある。記録が誤って確定することはない(新しいリンクで、もう一度行う)。

## ブラウザからの読み書き(RLS。0003・0024 のポリシーを作り直した)
- salons
  - 参照・更新は、信頼できるセッションの所有者だけ。
  - 更新できる列は区分で変わる(制限のトリガー)。
    - 利用開始待ち: 店舗名・業種・連絡先だけ
    - 利用中: 0011 の列に連絡先を足したもの
  - 追加と削除のポリシーは削除した。店舗の作成は RPC だけ。
- surveys / questions / question_options
  - オーナーの操作は、口コミを使える店舗(`owner_feature_salon_ids('reviews')`。区分・プラン・提供状態・個別設定を含む)だけ。アンケートの RPC は security invoker なので、同じく止まる。
  - 公開中のアンケートは、`salon_reviews_public_available` の店舗だけ。
- salon_feature_overrides: 信頼できるセッションで、利用中の区分の店舗だけ。
- ブラウザのロールが実行できる security definer の関数
  - `create_own_salon`・`my_account_state`・`owner_*_salon_ids`(authenticated)
  - `salon_reviews_public_available`(anon・authenticated)
  - 0009 の `notifications_mark_retry_outcome`(security invoker)は、書き換え禁止のため残した。対象の表にブラウザ向けのポリシーが無く、何も変えられないことを localdb で確かめた。
- LINE の招待: `line_invite_status` は、利用中ではない店舗の招待を `unavailable` にする(受付・開始・登録のすべてに効く)。
- 入口ごとの確認
  - Google OAuth の callback・Google の連携の操作: 利用開始待ちなら止める。
  - `/api/review-events`: 口コミを使えない店舗は記録しない。
  - 生成 API: 使えない店舗は従来どおり 403。

## 運営のサロンの追加・招待
- **下書き** `salon_drafts`
  - salons に入れない。アカウントも作らず、メールも送らない。
  - サロン名だけで保存できる。版数で同時の編集を検出する。
- **本登録**(`registerSalonAction`)。順に行う。途中で失敗しても、もう一度実行すれば重複せずに続きから進む。
  1. 紐付け先を用意する(`lib/onboarding/accounts.ts`)
     - 新しいアドレス: パスワード無しで作り、`set_new` にする。
     - 未確認: パスワードを乱数にして無効にし、`set_new` にする。
     - 確認済み・本人確認済み: そのまま。パスワードは変えない。
     - 確認済みなのに本人確認がまだ、管理者、店舗を持つ: 紐付けない。
  2. `admin_register_salon`
     - 店舗・個別設定(対象プランの機能だけ。プランが未定なら無し)・招待の行・履歴を、1つのトランザクションで書く。
     - 登録種別は通常登録(利用開始待ち)かテスト用だけ。新しい店舗は無料提供にできない(0026)。
     - 同じ下書きなら同じ店舗を返す。
     - 所有者ごとの advisory lock は `create_own_salon` と同じ鍵。
  3. 初回の案内(`lib/onboarding/invitation.ts`)
- **案内の種類**: テンプレート1つにつき用途は1つ。
  - 未確認のアカウント: 招待
  - 本人確認済み: 店舗登録のお知らせ(Magic Link)。本人確認が済んでいても送る。
  - 確認済みで本人確認がまだ: 本人確認のリンク(Reset password。お客様にはパスワード再設定と同じ形式のメールで届く。画面と運営の画面で、そのことを伝える)
- **再送**: 60秒あけ、24時間で10回まで(DB で確かめる)。「送信を受け付けた」は、届いた・読まれたという意味ではない。
- **「招待手続き完了」の根拠**: メールが確認済み、かつ本人確認の記録がある。利用区分とは別に表示する。

## メールの送信の制御(`lib/onboarding/authEmailPolicy.ts`・`authEmail.ts`)
- 送らない環境: 開発・プレビュー・testdb。
- verify(`AUTH_EMAIL_VERIFY`)は、許可したアドレスにだけ送る。本番では送る。
- 今回足した・変えた送信の経路は、`authEmail.ts` だけ(静的テストで確かめる)。
- 既存のパスワード再設定(ブラウザから)は対象外。開発・テストでも Supabase の設定どおりに送られる。そのためテストでは、予約済みのドメイン(`example.invalid`)のアドレスだけを使う。

## 残るリスク・確かめていないこと
- (0026)Supabase の、同じ人への最低の間隔の実際の値は確かめていない。アプリの間隔(初期値65秒)より長い設定だと、受付と表示されてもメールが送られないことがある(応答は、登録済みかどうかを漏らさないため同じにしている)。
- (0026)新規登録を止めた状態(Supabase の「Allow new users to sign up」を OFF)で、運営の招待(`inviteUserByEmail`)が動くかは確かめていない。
- (0026)Supabase のプロジェクト全体のメールの上限・サーバーの IP にかかる上限は、アプリの待ち時間では表せない。
- (0026)テスト用の指定は、運営の判断で通常のお客様にも使えてしまう(DB では止めていない)。お客様の利用開始の代わりに使わないことは、画面の説明と運用で守る。
- 同じアカウントで、2つのメールのリンクから同時にパスワードを設定すると、どちらも「手続きのやり直し」になる(パスワードの変更が、もう一方のセッションを消すため)。安全側に止まり、新しいリンクからやり直せる(testdb で確かめた)。
- 確認前に孤立したアカウントが残ることがある(本登録が途中で失敗したとき)。パスワードも店舗も無く、ログインできない。同じアドレスで後から登録すると、再利用する。
- 第三者が先に作った未確認のアカウントでは、本人が本人確認を済ませるまで、第三者のパスワードで Supabase にはログインできる。ただし、SalonPack の画面・Action・店舗の DB の操作は止まる。これは、未認証の人の再登録ではパスワードを変えない、というユーザーの決定による。
- 確かめていないこと
  - 実際のメールの送信と到達
  - テンプレートの見た目
  - 本番の Supabase Auth の動き(読み取った設定以外)
  - 実際の環境でのメールの先読み
  - パスワード再設定の `/recover` そのもの(GoTrue がトークンを作って送る部分。上の通しの確認では、同じ状態を用意して置き換えた)
  - パスワードを変えたときの Supabase のお知らせのメール(Security notifications の「Password changed」。有効なら、再設定・本人確認のたびに送られる)
