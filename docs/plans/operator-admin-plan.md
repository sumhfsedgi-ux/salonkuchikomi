# 運営管理(システム管理者)・機能ごとの利用権限 — 設計

作成: 2026-10-12。branch: `claude/salonpack-admin-system-plan-mhj3va`(master 2e850b5 から)。本番反映の手順は `docs/plans/operator-admin-runbook.md`。

## 目的と範囲
- 運営が、各サロンの契約プランと機能ごとの利用許可を、管理画面(`/ops`)で管理する。
- 含む: 管理者専用アクセス、サロン一覧・詳細、契約変更、機能ごとの利用許可、連携状況の閲覧、操作履歴、権限による停止の解除。
- 含まない: 管理者の追加・削除の画面(CLI `scripts/operator-admin.ts`)、プラン標準の編集画面(migration で変更)、届いた口コミ・AI返信(`google_reviews` はカタログに入れず、今まで通りコードの `PLAN_FEATURES` で判定)。

## 確定した運用ルール
| 項目 | ルール |
|---|---|
| 口コミプラン | 口コミだけ。ブログ・予約通知は SalonPack に変更して使う(口コミプランのまま個別許可はできない) |
| SalonPack | 対象機能をサロンごとに許可・解除できる |
| 判定の軸 | 提供状態(準備中/提供中/提供終了)・対象プラン・プラン内の標準・サロン個別設定を分ける。個別設定で対象プラン・提供状態の制限は解除できない |
| プラン変更 | 個別設定は残す。変更後のプランで対象外になる設定は効かない(画面と保存前の確認に表示) |
| 口コミの停止 | 設定画面・変更操作・お客様用ページ・生成 API を止める(直接アクセスでも)。お客様用ページは「現在ご利用いただけません」(理由は出さない)。サロン利用者には停止中の画面(サロン設定・ログアウトは使える)。データは消さない。再許可で元の設定のまま使える |
| 予約通知 | 利用不可で「権限による停止」を記録し、再許可だけでは再開しない。解除は運営が管理画面から行う。受信ON/OFF・お客様の利用停止・運営による停止・旧側の切り替え条件は解除しない。CLI の契約変更も同じ。停止期間中に届いた予約は送らない(既存の仕様)。停止前に届いた未送信の予約は既存の規則(24時間以内なら送る)のまま |
| 管理者 | サロンオーナーとは別のアカウント。判定は認証済みユーザー ID(`operator_admins`)。メールアドレスの一致では判定しない |

## データ構造(`supabase/migrations/0024_operator_entitlements.sql`)
| 表・関数 | 内容 |
|---|---|
| `feature_catalog` | 機能 ID・提供状態(lifecycle)・定期処理を持つか(has_runtime)。表示名・アイコン・分類・表示順・前提条件はコード(`lib/features/registry.ts`)に持つ |
| `plan_feature_rules` | 行がある=そのプランの対象。`default_enabled`=プラン内の標準 |
| `salon_feature_overrides` | allow / deny(行が無い=プランに従う)。オーナーは自店舗分を読めるだけ |
| `salon_entitlement_state` | 店舗ごとの基準行(版数・前回コミット時点の利用可否)。共通のロック |
| `salon_feature_holds` | 権限による停止(予約通知)。運営の解除(`feature_hold_release`)だけで閉じる |
| `operator_admins` | 管理者(ユーザー ID)。ブラウザのロールから読み書きできない |
| `operator_audit_log` | 操作履歴(追記のみ。UPDATE・DELETE・TRUNCATE を拒否)。変更と同じトランザクションのトリガーで書く |
| `salon_feature_access(_all)` | 最終的な利用可否と理由。画面・API(アプリは結果を読むだけ)と予約通知の DB 関数が同じ関数を使う |
| `admin_update_salon_entitlements` | 契約と個別設定の保存(版数と値の両方を比べる。管理者かを DB でも確認) |
| `salon_public.reviews_available` | お客様用ページ・生成 API 用の真偽値だけ(理由は返さない) |

## 整合性
- **ロックの手順**: 契約・個別設定・提供状態・プランの標準を変える経路(管理画面・CLI・SQL Editor)はトリガーで基準行を `FOR UPDATE` し版数を上げる(店舗の行 → 基準行の順)。`notifications_begin_send`・`claim`・`gmail_scan_acquire`・`customer_start`・`reservation_ops_activate` は基準行を `FOR SHARE` してから利用可否と停止を読む。→ 利用不可の保存が完了した後に、新しい送信開始(`send_started_at`)は起きない。保存の時点で送信開始済みのものは取り消せないため件数を返して表示する。
- **停止の開閉はコミット直前に1回**(遅延制約トリガー `salon_entitlement_settle`): 途中の状態では開閉しない。評価は `committed_entitled` だけを書き版数を変えないため再起動しない。何度変えても停止・停止期間・履歴は1件。
- **同時編集**: 版数の行は全店舗に事前に作る(作成時のトリガー・保存関数でも作る)。保存は版数と画面を開いた時点の値(プラン・全機能の個別設定)の両方を比べ、違えば何も書かない。CLI・SQL の変更もトリガーで版数が上がる。
- **全体の変更**: `feature_catalog`・`plan_feature_rules` の変更は、対象の全店舗の基準行の版数を上げ、各店舗をコミット直前に評価する(利用可→不可なら停止を開く。戻しても自動で再開しない)。
- **旧アプリとの互換**: 既存の関数は引数の形を変えない。`p_allowed_plans` に配列が渡されたら従来どおり AND 条件にする(新しいアプリは null)。

## 画面
- `/ops/salons`: 店舗名・登録メールで検索、プラン・機能の利用可否で絞り込み、50件ずつ。
- `/ops/salons/[id]`: 基本情報(閲覧)/ 契約と利用許可(下書き → 確認(変更内容と影響)→ 保存)/ 連携と稼働状況(閲覧。権限による停止の解除だけ操作)/ 変更履歴。
- ログイン: 通常の `/login` → `/dashboard` の layout が、サロンを持たない管理者を `/ops/salons` へ移す。`createSalonAction` は管理者を拒否する。
